# alf-code-node-validator

> **이 문서는 도구 소개서가 아니라, 이 프로젝트가 왜 채택되지 않았는지 분석한 기록이다.**
> 한 문장으로: **구현이 아니라 문제 정의를 잘못해서 실패했고, 그 원인을 분석했다.**

이 프로젝트는 채널코퍼레이션 "AX 인재전쟁" 예선 제출작이다. 도구 자체는 실제로 동작했지만 본선에 오르지 못했고, 이 README는 "무엇을 만들었나"보다 **"왜 떨어졌나"**에 지면을 쓴다.

## 1. 프로젝트 소개

**무엇을 만들었나** — 채널톡 ALF(FrontALF) *Code node*에 들어가는 JavaScript가, [공식 문서](https://developers.channel.io/en/articles/Code-node-fdcd71b4)에 명시된 숨은 제약(아래 R1~R6)을 지키는지 **배포 전에** 검사하는 Codex 플러그인.

**어떤 문제를 풀려 했나** — ALF Code node는 일부 제약을 위반해도 작성 시점엔 오류가 안 나고, 실제 실행 단계에서만 조용히 실패한다(예: `memory.save()` 누락 시 데이터가 저장되지 않음). 이 조용한 실패를 배포 전에 자동으로 걸러주려 했다.

**기술** — 공식 문서 인용 기반 규칙셋 + Python 정적 스크립트(1차 스캔) + Codex SKILL 수동 검사(최종 판정). 구성 자체는 단순하다.

## 2. 왜 이 문제를 선택했는가

당시에는 **"공식 문서에 근거가 있는 문제일수록 설득력이 높다"**고 생각했다. "어겨도 에러가 안 나는" 제약이라 개발자가 빠질 함정처럼 보였고, 규칙이 명확해 짧은 시간 안에 완성할 수 있다는 점도 골랐던 이유다.

결국 우리가 고른 기준은 **"근거를 대기 쉽고, 완성 가능한 문제"**였다. 이 기준 자체가 뒤에서 실패의 핵심이 된다(4·5장).

## 3. 무엇을 만들었는가

### 검사 규칙 (R1~R6)

| 규칙 | 내용 |
|---|---|
| R1 | 언어 = JavaScript인가 |
| R2 | 60초 안에 끝날 구조인가 |
| R3 | 금지 함수·라이브러리를 사용하지 않는가 |
| R4 | isSandbox 분기에서 외부 네트워크 호출을 안 하는가 |
| R5 | `memory.put()` 뒤 `memory.save()`가 있는가 |
| R6 | 함수 시그니처(인자 순서)가 올바른가 |

각 규칙은 `위반` / `위반 없음` / `확인 불가` / `해당 규칙 대상 아님` 네 가지 상태로 표기한다.

### 왜 2단계 구조인가

정적 패턴 매칭 스크립트 하나만으로는 R1(언어)·R3 금지 함수 전체 목록·R6(인자 순서)·분기별 `save` 누락을 못 잡는다. 그래서 검사를 둘로 나눴다.

- **1단계 — 결정론 정적 스크립트** (`src/scripts/validate_code_node.py`): 텍스트 패턴을 빠르게 1차 스캔. 같은 입력이면 항상 같은 결과.
- **2단계 — SKILL 수동 검사** (`verify-alf-code-node`): 1단계가 놓치는 부분을 공식 문서와 직접 대조. **최종 판정은 반드시 여기서 내린다.**

판정 기준을 실행 시점 AI의 즉흥 판단이 아니라 문서 인용에 고정하려 했고, 문서에 근거 문장이 없으면 위반이라 단정하지 않고 "확인 불가"로 남기는 폴백을 뒀다(지어내지 않기).

### 실제로 동작한다 — 리포트 예시

`@verify-alf-code-node`에 아래 Code node JS를 넘기면 이런 리포트가 나온다. (전체 실행 로그: `tests/results.md`)

**입력:**
```javascript
export const handler = async (context, memory, isSandbox) => {
  if (isSandbox) {
    memory.put('smallTalk', 'bigResult');
    memory.save();
    return;
  }

  setTimeout(() => {
    console.log('polling check');
  }, 100);

  memory.put('smallTalk', 'liveResult');
}
```

**1단계 — 자동 스크립트:**
```
검사 결과: 0건 발견
정적 검사에서 위반 후보를 찾지 못함.
```
→ 자동검사만 보면 "통과"처럼 보인다.

**2단계 — R1~R6 수동 검사 (최종 판정):**

| 규칙 | 판정 | 근거 |
|---|---|---|
| R1 언어 | 위반 없음 | JavaScript 문법 |
| R2 60초 | 위반 없음 | 무한 루프·대량 반복 없음 |
| **R3 금지 함수** | **위반** | `setTimeout(...)` 호출 — 금지 함수 목록. references: "…setTimeout, setInterval…" |
| R4 isSandbox | 해당 규칙 대상 아님 | 분기 내 외부 네트워크 호출 없음 |
| **R5 save 누락** | **위반** | else 분기의 `memory.put('smallTalk','liveResult')`에 대응하는 `memory.save()`가 없음(isSandbox 분기엔 있어 파일 전체 검사로는 안 잡힘 → 분기별 확인 필요). references: "If you only call memory.put() without calling save(), changes will not be saved." |
| **R6 인자 순서** | **위반** | 시그니처가 `(context, memory, isSandbox)` — `memory`가 첫 번째 인자여야 함 |

자동 스크립트만 돌렸다면 이 3건(R3·R5·R6)은 그대로 배포됐을 것이다. 만들려던 도구는 설계대로 동작했다.

## 4. 결과

**채택 결과 (명확히):** AX 예선에 제출 → 참가작 5,300여 건 중 **상위 약 10%** 성적으로 "AI 인재"에 선정 → 그러나 **본선(60선) 진출 컷에는 미달**. 즉 본선에 오르지 못했다. ("상위 10%"와 "본선 탈락"은 모순이 아니라 같은 예선 트랙 안의 등급 차다.)

**왜 채택되지 않았나 — 세 가지로 구분한다:**

| 후보 원인 | 판정 | 근거 |
|---|---|---|
| 구현이 부족했나 | ❌ 아니다 | 도구는 실제로 동작했다(3장 리포트 예시). 정직성·결정론 설계는 오히려 채점의 강점 축에 부합했다 |
| 기술 선택이 틀렸나 | 🔶 부분적 | 검사 상당수는 전용 린터/파서로도 가능해 "왜 굳이 AI인가"가 약했다. 다만 이건 치명타는 아니었다 |
| **문제 선정이 틀렸나** | ✅ **그렇다 — 최대 원인** | "제약이 문서에 존재한다"만 근거로 삼고, "이 위반이 실무에서 자주·비싸게 난다"는 문제의 실재성을 제3자 증거로 입증하지 못했다 |

세 번째가 결정적이었다고 본다. 공개된 심사 기준을 다시 읽어보니 우리가 가장 크게 놓친 건 "확인 가능한 출처"였다. 그 기준이 요구한 건 *제약이 존재한다*가 아니라 *그 문제가 실제로 자주 일어난다*는 증거였다. 우리는 문제를 현장에서 **관측**한 게 아니라 문서에서 **연역**했고, 그래서 앞만 증명한 채 뒤를 비워뒀다.

**구현이 아니라 문제 선정이 더 큰 실패 원인이었다.** 잘 푼 게 문제가 아니라, 풀 문제를 잘못 골랐다.

## 5. 회고

가장 오래 남은 깨달음은 하나였다.

**우리는 문서에 존재하는 문제를 증명했을 뿐, 실제로 사람들이 겪는 문제를 증명하지는 못했다.**

문서에 적힌 제약을 찾는 일은 쉬웠지만, "그래서 이게 현장에서 진짜 자주 불편한가"를 검증하는 건 완전히 다른 일이었다. 이후부터는 무엇을 만들지보다 어떤 문제를 풀어야 하는지를 먼저 검증하는 방식으로 접근을 바꿨다. 그 문제 선정 과정을 반복 가능한 방법으로 만들려고 다음 프로젝트를 진행했다.
